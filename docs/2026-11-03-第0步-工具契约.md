## 0. 一句话

**出生的是“会动手的 agent”，不是“会聊天的 agent”。** 手 = 工具层。第 0 步只做一件事：把工具的**定义、执行、门禁、结果**四件事钉死，后面所有工具都照同一个模子长。

M0 只有四个真工具：

| 工具 | 一句话 | 风险 |
|---|---|---|
| `read` | 读一个文本文件，或列一个目录 | low（敏感文件名升 high） |
| `write_file` | 整文件写入 | high |
| `edit_file` | 精确替换一段原文 | high |
| `shell` | 执行一条命令 | high |

`echo` 只是 T4 的联调假工具，不进最终清单；glob / grep 按 M0 计划留到 M1。

本文档不写实现、不排任务、不碰 UI。实现仍在 T4–T7，按《编码规范与协作约定》由你写。它只回答四个问题：**工具长什么样、怎么被调用、什么时候要人点头、出错时怎么说话。**

## 1. 判断：工具 ≠ bash 命令

在 M0 里，`git status` 不是工具，它是 `shell` 工具的一次调用。反过来，`read` 也不是 `cat` 的别名——它是一个独立工具。

| 维度 | 只给 bash | 结构化工具 + 一个 shell |
|---|---|---|
| 参数 | 一个字符串，靠模型自己拼 | JSON Schema，可校验、可拒绝 |
| 权限 | 一刀切：要么事事问，要么全放行 | 按工具与参数分级 |
| 输出 | 原始文本，不可控 | 预算截断 + 续读提示 + metadata |
| 跨平台 | 依赖 cat / sed 是否存在 | `node:fs` 自带 |
| 审计 | 只能存命令文本 | 结构化参数与结果可核对 |
| 模型理解 | 要记住命令语法 | 描述与参数就是说明书 |

三条原则：

1. **能用专用工具表达的，不走 shell。** 专用工具可校验、可分级、可预算；shell 什么都能干，所以最危险。
2. **shell 是通用逃生口，不是默认入口。** 它保留，因为要跑 `pnpm typecheck`、`git status` 这类没有专用工具的命令。
3. **模型看到的是定义，不是实现。** read 内部用 `node:fs` 还是别的，模型不知道也不需要知道。

## 2. 一个工具的四件事

| 层 | 内容 | 谁看 |
|---|---|---|
| 定义 | `name` / `description` / `parameters`（JSON Schema） | 模型。这是它唯一能看到的工具全貌 |
| 执行 | `execute(args, context)` | kernel。模型看不到实现 |
| 门禁 | 风险等级 + 确认预览 | 权限层与 CLI。决策权在 CLI |
| 结果 | `ToolResult` | 模型读 `content`；会话与调试读 `metadata` |

```
模型 ──tool_call(JSON)──▶ kernel 循环
                           │
                           ├─ 查 registry：拿到定义与风险基线
                           ├─ low  ─────────────────────▶ execute
                           └─ high ─▶ 待确认事件 ─▶ CLI 展示 ─▶ y / n
                                                          │
                                          n ──▶ 拒绝结果回喂，循环继续
                                          y ──▶ execute
                           execute 返回 ToolResult ──▶ role:"tool" 回喂
```

工具自己的边界（违反任何一条都算设计错误）：

- **不打印**：结果只返回，怎么显示是 CLI 的事。
- **不读 stdin**：确认由权限层统一做，工具不许自己问。
- **不退出进程**：失败也要返回结果，让循环决定下一步。
- **不互相调用**：工具是叶子；`read` 内部的文件/目录两条分支也不互相调用，组合由模型多轮调用完成。
- **不越界**：文件类工具的根是仓库根；跨出根目录一律报错。

## 3. 契约 v0

形状示意，T4 实现时按这个来，不是让你照抄：

```ts
interface ToolDefinition {
  name: string;                    // 全项目固定，snake_case
  description: string;             // 何时用 / 何时不用 / 返回什么
  parameters: JsonSchema;          // 参数校验的唯一依据
  riskLevel: "low" | "high";       // 风险基线，权限层可升不可降
}

interface Tool {
  definition: ToolDefinition;
  execute(args: unknown, ctx: ToolContext): Promise<ToolResult>;
  riskOf?(args: unknown): RiskLevel; // 按参数细化风险：只能在基线之上升，不能降
  preview?(args: unknown): string;   // 高风险工具的确认预览：diff / 命令 / 路径警告
}

interface ToolContext {
  root: string;                    // 仓库根，所有相对路径的基准
  signal?: AbortSignal;            // Ctrl+C 或超时取消
}

interface ToolResult {
  content: string;                 // 成功 = 结果；失败 = 错误教程
  isError: boolean;
  metadata?: Record<string, unknown>; // 事实数据，不自动进模型上下文
}
```

四条硬规则：

1. **`description` 必须写“何时不用”。** 只写“读取文件”会让模型拿它去读二进制；要写“不要用它读图片或二进制，内容过长会截断并给 next_offset”。
2. **参数校验在 `execute` 入口做。** 不信任模型给的任何字段：类型、范围、路径都要查，错了返回 `E_INVALID_PARAM`。
3. **成功与失败走同一条返回通道。** 失败不是抛异常穿透内核，而是 `isError: true` 的 `ToolResult`，以 `role:"tool"` 回喂模型，让它自己改道。
4. **截断事实既进 `metadata`，也要写进 `content`。** 模型只看 `content`；不写“已截断、续读 offset=N”，它就会以为自己看完了。

`content` 的错误格式固定为两行，第二行必须是可执行的下一步：

```
[E_EDIT_NO_MATCH] 在 packages/cli/src/repl.ts 中没有找到 old_string。
下一步：先 read 重新读取该文件，确认缩进与换行完全一致；仍找不到就缩小 old_string 的范围。
```

## 4. 四个工具的规格

> 实现状态：`read` 已完成（`packages/tools/src/read/`），其余三个待 T6 / T7。

### 4.1 read

**一个工具，按路径类型分流**：文件 → 读内容，目录 → 列条目。对外只有 `read` 一个名字，模型不需要先知道路径是文件还是目录。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `path` | string | 是 | 仓库根相对路径；绝对路径必须落在根内 |
| `offset` | number | 否 | 仅文件模式：起始行，1 起，默认 1 |
| `limit` | number | 否 | 仅文件模式：最多读多少行，默认吃满预算 |

文件模式行为：

1. 路径先做根内校验，越界直接 `E_OUTSIDE_ROOT`，不尝试“修正”。
2. 体积门禁：`stat.size > 1 MB` 直接 `E_TOO_LARGE`，M0 不做流式读。
3. 二进制判定：前 8 KB 出现 NUL 字节 → `E_KIND_UNSUPPORTED`；UTF-8 BOM 去掉，UTF-16 不接。
4. 行号始终打开，格式 `   12\t内容`（宽度 6、右对齐）；行号是读取时刻的坐标，不是编辑依据。
5. 行尾按原样识别（LF / CRLF），不改写；`metadata` 带 `eol`。
6. 行数 / 总字符 / 单行宽度三重截断；截断后 `content` 写清楚已显示范围、总行数与 `next_offset`。
7. `metadata` 带 `kind: "file"`、`mtime`、`size`、`totalLines`、`eol`、`truncated`、`nextOffset`、`lineWidthTruncated`。
8. 敏感路径（`.env`、`.env.*`（`.env.example` 除外）、`*.pem`、`id_*`）风险升为 high，确认文案要写明“此文件可能含密钥”。

目录模式行为：

1. v0 只做列表，不生成结构树；不递归。
2. 固定跳过 `.git` 与 `node_modules`，避免一屏全是噪声。
3. 输出每行一个条目：`[dir] src/` 或 `[file] README.md  2.9 KB`；目录在前，同类型按名称排序。
4. 条目数或输出字符超预算时，明确写“还有 N 个未列出”，不静默丢。
5. 目录模式下传了 `offset` / `limit` → `E_INVALID_PARAM`，不静默忽略。
6. `metadata` 带 `kind: "dir"`、`entryCount`、`truncated`、`omittedCount`。

### 4.2 write_file

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `path` | string | 是 | 仓库根相对路径 |
| `content` | string | 是 | 完整文件内容 |

行为：

1. 这是整文件写入，不是追加；覆盖已有文件时，确认预览必须是完整的 unified diff。
2. 按给定内容原样写 UTF-8，不做行尾转换，不自动补末尾换行。
3. 父目录不存在时返回 `E_PARENT_MISSING`，不自动建目录（待 §11 拍板）。
4. 超过 1 MB 返回 `E_TOO_LARGE`，不写半截文件。
5. 成功后 `metadata` 带 `bytesWritten` 与 `created`（新建还是覆盖）。

### 4.3 edit_file

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `path` | string | 是 | 仓库根相对路径 |
| `old_string` | string | 是 | 要被替换的原文，必须非空 |
| `new_string` | string | 是 | 替换后的文本，可以为空（表示删除） |

行为：

1. 精确字符串匹配，不做正则、不做模糊、不做空白归一化。
2. **必须唯一匹配**：0 处报 `E_EDIT_NO_MATCH`，多处报 `E_EDIT_NOT_UNIQUE`，都不猜。
3. 只替换那一处，其余字节保持原样；原文件的行尾风格不改。
4. 确认预览是这一处替换的 unified diff，不是整个文件。
5. 成功后 `metadata` 带 `replacements: 1` 与字节增减。

“不猜”是这里的核心：宁可报错让模型重读，也不替它决定改哪一处。

### 4.4 shell

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `command` | string | 是 | 要执行的命令原文 |
| `timeout_ms` | number | 否 | 默认 120000，上限 600000 |

行为：

1. `cwd` 固定为仓库根，M0 不接受自定义工作目录。
2. 通过系统默认 shell 执行：Windows 上通常是 cmd，POSIX 上是 sh；`bash` 只是其中一种，不是前提。
3. stdin 关闭；需要交互输入的命令会一直等到超时，这是预期行为，不特殊处理。
4. stdout 与 stderr 分开收集；输出超预算时保留头部与尾部，中间标注省略的字符数。
5. **退出码非 0 不是工具错误。** 命令跑完了、只是失败：`isError: false`，`metadata.exitCode` 如实带出，模型必须如实汇报。工具错误只留给“没跑起来”（`E_SPAWN_FAILED`）或“超时被杀”（`E_TIMEOUT`）。
6. 超时杀整棵进程树，不只杀父进程；否则 Windows 上会留下孤儿进程。
7. 每次执行都确认，预览是完整命令 + cwd + 超时；M0 不做命令黑名单，确认就是门禁。

## 5. 权限：决策权在 CLI

链路固定为：

```
模型 tool_call → kernel 查风险 → high 则发“待确认事件”
→ CLI 渲染 preview、收 y/n → 把 decision 交回 kernel
→ allow 执行 / deny 产出拒绝结果并回喂模型
```

事件形状示意：

```ts
interface PermissionRequest {
  request_id: string;
  tool_name: string;
  args: unknown;
  risk_level: "high";
  preview: string;   // 工具已渲染好的 diff / 命令 / 路径警告
  reason: string;    // 为什么需要确认，一句话
}

interface PermissionDecision {
  request_id: string;
  decision: "allow" | "deny";
}
```

规则：

1. **kernel 不碰终端。** 它只发事件、等决定；打印与按键都在 CLI。这样 M1 的桌面端能复用同一套事件，只换 UI。
2. **风险是 (工具, 参数) 的函数。** 工具给基线，权限层可按参数升级：`read` 平时 low，命中 `.env` 升 high；`shell` 永远 high，不允许降级。
3. **拒绝也是正常结果。** 返回 `E_PERMISSION_DENIED`，hint 写“用户拒绝了这次操作，不要重试同一操作；先说明意图，或换一种做法”，让模型改道，而不是把循环卡死。
4. **每次调用都留痕。** assistant 的 tool_call 与 role:"tool" 的结果都进会话；确认决定与耗时记在该工具消息的 `metadata` 里。

M0 不做“本会话内允许同类操作”（待 §11 拍板）；高风险操作逐次确认。

## 6. 预算红线

| 位置 | 默认预算 | 超限行为 |
|---|---|---|
| read（文件模式） | 2,000 行 / 60,000 字符 / 单行 2,000 字符 / 文件 1 MB | 截断 + 自报 + `next_offset`；超 1 MB 直接 `E_TOO_LARGE` |
| read（目录模式） | 500 条目 / 50,000 字符 | 截断 + 点名剩余数量 |
| write_file | 1 MB | `E_TOO_LARGE`，不写 |
| edit_file | 目标文件 1 MB | `E_TOO_LARGE`，不读 |
| shell | 120 秒（可传 `timeout_ms`，上限 600 秒）/ 输出 64 KB（头 32 KB + 尾 32 KB） | 超时杀进程树；输出标注省略 |
| 单次回喂 | 64 KB | 工具先截断，再交给循环 |

这些数是第一版默认值，T5 联调后可调；三条结构不变：**有预算、超限自报、可续读或可缩小范围**。阈值集中放在一个常量文件，不在调用点写魔法数字。

## 7. 错误码

| 错误码 | 触发场景 | hint 应指向 |
|---|---|---|
| `E_INVALID_PARAM` | 参数缺失、类型错、范围错 | 按 schema 补齐或修正 |
| `E_OUTSIDE_ROOT` | 路径越出仓库根 | 改用根内相对路径 |
| `E_NOT_FOUND` | 路径不存在 | 先用 read 列出父目录，确认路径 |
| `E_TOO_LARGE` | 超过硬上限 | 分段读，或改用 shell 做流式处理 |
| `E_KIND_UNSUPPORTED` | 二进制、非文本 | 不要用 read 读它，改用 shell 的专用命令 |
| `E_DECODE` | 文本解码失败 | 说明编码，换工具处理 |
| `E_IO` | 系统 IO 异常 | 检查权限与文件状态 |
| `E_PARENT_MISSING` | 父目录不存在 | 先确认再创建目录 |
| `E_EDIT_NO_MATCH` | 旧串 0 处匹配 | 重读文件，逐字复制原文 |
| `E_EDIT_NOT_UNIQUE` | 旧串多处匹配 | 带上更多上下文，使匹配唯一 |
| `E_TIMEOUT` | 命令超时被杀 | 缩小命令范围，或显式加长 timeout |
| `E_SPAWN_FAILED` | 进程没起来 | 检查命令是否存在、能否执行 |
| `E_PERMISSION_DENIED` | 用户拒绝 | 不要重试同一操作，说明意图或改道 |
| `E_ABORTED` | 用户 Ctrl+C 中止 | 停止当前动作，等待新指令 |

错误码一旦定下就稳定，不改含义；新增错误码只能追加。

## 8. 命名与词汇表

| 词 | 含义 | 不要叫 |
|---|---|---|
| tool | 模型可调用的一个能力 | function、command（指工具时） |
| tool_call | 模型请求调用工具的结构化消息 | 工具请求、调用命令 |
| tool_result | 工具执行结果，回喂模型 | 工具返回值、输出（易与 stdout 混） |
| registry | 工具注册表，定义唯一定义处 | 工具池、工具列表 |
| permission | 权限门禁 | 审批、授权（代码里统一用 permission） |
| confirmation | 高风险操作前的人工确认 | 弹窗、询问 |
| session | 一段对话及其落盘 | conversation、chat |
| kernel | 模型循环、会话、权限、provider | core、engine |
| cli | 终端壳 | 客户端（M2 的 host/client 语境再用） |

工具名固定为 `read` / `write_file` / `edit_file` / `shell`，不改名、不新增别名。**模型可见的字段（工具名、参数名、参数 schema）一律 snake_case；`metadata` 是代码侧数据，用 camelCase。** 代码内部变量 camelCase。

## 9. 与 MCP 的兼容

M0 不接 MCP，但契约按 MCP 的形状留口：

- MCP 的工具定义也是 `name` / `description` / `inputSchema`，与本文的 `ToolDefinition` 一一对应；
- M2 时，MCP server 的工具可以直接注册进同一个 registry，与本地工具同权；
- 权限检查仍由我们自己做，MCP server 不能绕过确认；
- `ToolResult` 的 `content` 以后可扩展为内容块（文本 / 图片），M0 先只做文本。

不要现在手写 MCP 协议；M2 直接接官方 SDK。现在要保证的只有一件事：**工具定义与注册表只有一处**，不要散落在各模块里。

## 11. 开放问题（拍板用）

1. **read 碰到敏感文件怎么办？**
   建议：升为 high，确认后允许；`.env.example` 例外。理由：直接一律拒绝会被 `shell cat .env` 绕过，不如让确认 UI 成为唯一的门。
2. **Windows 上的 shell 用哪个？**
   建议：M0 默认 cmd（Node `shell: true` 的默认行为），M1 再做可配置的 PowerShell；理由是 pnpm / git 在 cmd 下行为最稳定，避开 PowerShell 执行策略的坑。
3. **write_file 父目录不存在，报错还是自动创建？**
   建议：报 `E_PARENT_MISSING`，不自动创建；需要建目录时走 shell 并确认。理由：写工具只做它说的事，仓库结构变化留给用户点头。
4. **高风险确认是否提供“本会话内允许同类操作”？**
   建议：M0 不提供，逐次确认；M1 有 UI 后再加白名单。理由：M0 的确认次数不多，先把“每次都能看见”变成习惯。
