# skyPaws · 想法

> 随手记，先记下再整理。

## 定位

- **它是什么**：我以后的伙伴帮手（future companion），不是一个一次性工具。
- **展示命名**：skyPaws（云大脑就叫这个名字）
- **形态**：agent + harness（同类参考：Cursor、Claude Code、Codex）
- **愿景**：skyPaws 不只针对写代码——远期接入各种设备，成为贾维斯（Jarvis）式的个人智能中枢。现阶段从代码/文件工具起步；架构本身设备无关，加设备 = 换一套工具集上报。

## 架构雏形

- **云大脑 + 本地工具**：大脑（agent + LLM）放线上；工具跑在本地，云端可调用本地工具。
- **端只是工具**：桌面端 / web 端 / 移动端都只是「端」，端不装大脑，大脑始终在云上。
- **多端路线**：当前先做桌面端，后续扩展 web 端、移动端。
- **云上部署**：大脑（LLM）+ 会话记忆都部署到云服务器，随时可调用。
- **降级即对话**：就算身边没有任何工具，skyPaws 也能纯对话——大脑在，伙伴就在。
- **工具上报**：使用时由端（harness）告诉大脑当前有哪些工具可用。
- **每端一套工具**：电脑 A 一套工具、电脑 B 一套工具，但大脑只有一个，记忆互通。
- **动态工具切换**：大脑按当前在线端上报的能力集，动态决定这次对话/任务里能用哪些工具。

## 典型链路（跨端遥控）

- **绑定**：在公司电脑 A 启动工具（harness）并绑定大脑 → 大脑登记「设备 A 上线」，并建立会话通道（类似日常对话）。
- **遥控**：随后在手机 A 上发起对话，即可让大脑去操作电脑 A——手机不出工具，只是大脑的另一个对话入口。
- **链路**：手机 A（发指令）→ 云大脑 → 操作 → 电脑 A → 反馈 → 云大脑 → 显示 → 手机 A。
- **多设备并行**：A、B 电脑同时在线也不冲突——用户选择对哪个设备对话，大脑就按哪个设备的上下文操作。
- **渠道即窗口**：大脑 ↔ 每台设备的通道，本质上就是一个对话窗口；手机、电脑、web 端都是窗口的一种。大脑只有一个，窗口有很多个。
- **工具集挂在窗口上**：工具不属于大脑，属于窗口——电脑 A 的窗口带 A 的工具集，电脑 B 的窗口带 B 的工具集。大脑的记忆是全局的，工具是窗口内的。
- **大脑只发指令，设备才是执行者**：云大脑不执行任何工具，只往窗口里发指令；电脑 A 收到后在本地执行对应工具，结果沿窗口反馈回大脑。
- **工具所有权全在 harness**：skyPaws 自身没有任何执行工具的能力，只有「下发」；所有工具都是 harness 自己的——哪怕将来收编 MCP server 这类现成工具，也是挂进 harness 本地、以自己的名义上报，大脑永远只面对一份统一的工具清单。
- **连接时选工具**：harness 连接大脑时可以选择这次带哪些工具上线——同一台设备，针对不同项目挂不同的工具集。
- **语言解耦**：架构分离后，大脑和 harness 可以用不同语言开发——两边只靠协议约定，语言随便选。

## 群聊模型

- **消息全员可见**：在手机上发「帮我创建一个文件 xxx.md」，电脑 A 的对话列表也要同步显示这条消息——像微信群：任一端发言，所有在线端都看得见。
- **大脑是群成员**：skyPaws 是群里的一员，也是唯一有手的成员——看到消息后决定用哪个窗口的工具去执行。
- **推论**：每个在线窗口必须随时保持一条「能收消息」的通道（哪怕用户没在打字），否则跨端同步无从谈起。

## 协议（草案）：skyPaws ↔ harness

> 语言/框架先不定，协议保持语言中立。聊天通道（用户端）同走 WebSocket，消息格式后面单独细化；本节先定大脑 ↔ 工具。

### 传输选型：全 WebSocket

- **工具通道**：工具调用由大脑发起，设备随时上报进度——双向、随时、交织的流量必须一条连接搞定。SSE 半双工，上行要另开 POST，顺序 / 关联 / 断线恢复全要自己粘（MCP 早期 SSE+POST 踩过的坑，官方后来也换掉了）。
- **聊天窗口**：群聊模型要求每个在线窗口随时能收消息（跨端同步 + 大脑主动开口）。纯 HTTP+SSE 在请求间隙是哑的，要补常驻接收流，等于每端两条通道；WS 一条连接，服务端 fan-out 广播即可。
- **规模注**：HTTP+SSE 的基建红利（无状态水平扩展、CDN）是为百万级客户端准备的；个人伙伴几台设备，长连接管理成本约等于零。
- **会话恢复**：断线后凭 connection id + 消息序号补拉；手机后台断连是移动系统本性，系统级推送（APNs/FCM）以后单独接。

### 语义层：自定义 envelope（手搓）

- **决定**：不套 JSON-RPC 2.0 的信封，字段全部自定义——但把它的三条纪律偷过来：
  1. **callId 回带**：响应必须原样带回请求的 callId，多条调用乱序返回也能对上号（对应原仓库的「调用 id」）。
  2. **通知机制**：不需要回复的消息就是通知（如 `tool/progress`），发出后不等结果。
  3. **错误三件套**：失败统一 `{ code, message, hint }`，错误码沿用 `E_*` 那套。

### 最小消息集（7 条，先定这一圈）

| 消息 | 方向 | 作用 |
|---|---|---|
| `hello` / `welcome` | 设备→云 / 云→设备 | 连接 + 认证（token）+ 协议版本握手 |
| `tools/announce` | 设备→云 | 上报本次工具清单（「连接时选工具」靠它） |
| `tool/call` | 云→设备 | 指令：`{call_id, tool, args}` |
| `tool/result` | 设备→云 | 结果 / 错误，套 `ToolsResultVo`（`E_NOT_FOUND` 等错误码直接复用） |
| `tool/progress` | 设备→云 | 长任务进度（notification，不用回） |
| `ping` / `pong` | 双向 | 心跳 + 断线检测 |
| `bye` | 双向 | 窗口关闭 |

### envelope 示例

```json
// 云 → 设备（请求）
{ "type": "tool/call", "callId": 42,
  "payload": { "tool": "read_file", "args": { "path": "src/index.ts", "offset": 0 } } }

// 设备 → 云（响应）
{ "type": "tool/result", "callId": 42, "ok": true,
  "data": { "kind": "text", "content": "...", "truncated": false } }

// 设备 → 云（错误响应）
{ "type": "tool/result", "callId": 42, "ok": false,
  "error": { "code": "E_NOT_FOUND", "message": "文件不存在", "hint": "先 read_dir 确认路径" } }

// 设备 → 云（通知：进度，不要求回复）
{ "type": "tool/progress", "callId": 42,
  "payload": { "stage": "reading", "bytes": 51200 } }
```

### 与 MCP 的关系

- 不直接采用：MCP 拓扑是大脑侧主动连工具侧，本架构是设备反向拨云；hello / 绑定 / 多窗口 / 群聊广播 MCP 没有。
- envelope 是自定义的，与 MCP（JSON-RPC）不互通——但 `tool/call`、`tool/result` 的**载荷 schema** 保持对齐 MCP，日后接生态写一层字段映射即可。

## 大脑实现（手搓，不用框架）

- **LLM 无记忆，记忆是我们的**：模型 API 本身无状态；记忆 = skyPaws 自己存的会话/长期记忆 + 每轮自己组装上下文（system prompt + 记忆 + 近期消息 + 工具结果）。
- **不用 LangChain / LangGraph**：agent 主循环手搓——发请求（system prompt + 工具清单 + 消息）→ 模型返回 tool_calls → 下发 harness → 收结果 → 追加进消息 → 循环；没有 tool_calls 就直接回复。循环本身很小，框架的抽象在这里反而是负担。
- **请求手动发起或薄封装**：直接调模型 API，或自己封一层。
- （建议）内部定一个统一的调用接口：messages + tools 进，text / tool_calls 出——将来换模型供应商只换这一层。

## 功能清单（候选，待筛选）

> 按归属划分：大脑只长「想」的，harness 只长「做」的，协议只搬「话」的。

### 云大脑侧（纯决策与记忆）

- **长期记忆**：双层——会话日志 + 关于你的事实/偏好；可见、可纠正
- **多对话空间**：项目/话题分域，上下文隔离，长期记忆互通
- **定时与主动行为**：cron、主动开口——大脑常驻云端才有的能力
- **任务编排**：一个目标拆成多次 `tool/call`，跨窗口跟踪状态
- **人格一致性**：由记忆塑造的稳定性格

### harness 侧（全部执行与安全）

- **核心工具集**：read ✅（现仓库）→ glob/grep → write/edit → shell
- **权限分级**：安全读 / 需确认写 / 禁区；随 `tools/announce` 一并上报
- **跨端二次确认**：危险操作弹窗推到手机，一键批准/拒绝
- **工具档案**：「连接时选工具」的本地配置，按项目挂不同子集
- **长任务驻留**：执行器独立于聊天窗口，窗口断了任务不死
- **审计日志**：每次执行的记录（计时、callId、结果），可查
- （远期）**MCP 收编层**：挂现成 server，以自己的名义上报

### 协议侧（7 条消息的后续扩展）

- **设备状态广播**：上线/下线/掉线 → 群里通知
- **会话恢复 / 消息补拉**：connection id + 消息序号
- **系统推送接入**：APNs/FCM，手机后台可达

### 端侧（窗口体验）

- **群聊同步 UI**
- **设备面板**：在线设备 + 各自工具集清单
- **通知中心**

### MVP（skyPaws 先有的能力）

1. **对话能力**：纯对话就能用（呼应「降级即对话」）
2. **下发工具能力**：读取 harness 上报的工具集，下发 `tool/call`、收回 `tool/result`
3. **记忆**：会话持久化
4. **设备注册**：设备绑定大脑、登记在线状态

> 构建顺序注：下发工具依赖设备注册（先有设备在线，才谈得上下发）——实际开发时可在对话能力之后，先把设备注册的最小版（`hello` 绑定）立起来。
>
> **安全延后**：开发阶段先不做安全（认证、权限分级、白名单等），MVP 之后统一补。协议里的 token 字段留着占位即可。
>
> **施工顺序**：第一步先做 skyPaws（大脑），之后再做 harness。
>
> **大脑语言**：**Go**（已拍板）——理由：随时编译成单个二进制、内存占用小；Java 太重。Go 目前不熟，边做边学，学习本身就是这个项目的一部分。
