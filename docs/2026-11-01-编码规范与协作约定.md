# skyPaws-universe · 编码规范与协作约定

> 生效日期：2026-11-01　状态：生效中（对人和 AI 同样生效）
> 配套文档：[2026-11-01-项目方向与架构讨论.md](./2026-11-01-项目方向与架构讨论.md)

## 定位

这个项目的第一目标不是"尽快产出软件"，而是"学会亲手造它"。所以本规范优先服务学习效果，而不是开发速度。任何与此冲突的做法（哪怕更快）都默认错误。

---

## 规则一：项目不允许一次性生成完

**原则**：不做"一口气生成整个项目"这种事。一切增量推进。

**落实**：

- 路线是 里程碑（M0–M4）→ 任务 → 小步，每小步结束时代码都处于**可运行、可验证**的状态；
- 一次只推进一个任务，任务完成并验证后才开下一个；
- 对 AI 的约束：不倾倒大段代码，不"顺手"把后面的里程碑也写了；一次对话推进的量以一个任务为限。

## 规则二：以我写为主，AI 以教为主（最高优先级）

**原则**：这是学习项目，代码尽量由用户本人写出，而不是 AI 直接生成。

**角色分三档**：

| 档位 | 谁动手 | 适用场景 |
|---|---|---|
| 讲解 | AI 只讲不写 | 思路、方案对比、流程拆解、查文档、画结构图——默认档位 |
| 用户写 | 用户写，AI 不碰编辑器 | 所有核心逻辑、设计决策的实现 |
| AI 代写 | AI 写，但需先申请 | 仅限脚手架、样板代码、重复性劳动；写前说明"为什么这段可以代写"，写时小段给出、逐段讲解，写完用户要能合上屏幕复述出来 |

**执行细则**：

- AI 想写代码，先开口申请；用户明确说"你写"才算授权；
- 代写的代码在 commit 信息里注明（如 `scaffold: ai-assisted`），保持账目清楚；
- 衡量标准：这段代码写完，用户能不能不看它再写一遍？不能，就说明代写越界了。

## 规则三：注释 = 方法的流程说明书

**原则**：注释要写清楚"方法里发生了什么"，按步骤编号，像流程一样读下来。

**格式**（方法体内的步骤注释）：

```ts
export function loadConfig(path: string): Config {
  // 1. 读取配置文件原文
  const raw = readTextSync(path);
  // 2. 判断文件是否存在，不存在则抛出带修复提示的错误
  if (raw === null) throw new ConfigError("E_NOT_FOUND", path);
  // 3. 解析 yaml 并校验必填字段，缺字段直接报字段名
  const parsed = parseAndValidate(raw);
  // 4. 返回组装好的 Config 对象
  return new Config(parsed);
}
```

**细则**：

- 步骤注释说**业务动作**（"创建缓存目录"），不是把代码翻译一遍（"调用 mkdir 函数"）；
- 分支、循环、魔法数字必须有一句话解释"为什么"；
- 文件开头可以有 2–3 行注释说明这个文件在整个模块里的角色；
- 语言约定（延续旧 core 的习惯）：**注释用中文，标识符用英文**。

## 规则四：文件夹是模块，文件是职责

**原则**：不是一个文件一个模块，而是一个文件夹一个模块，里面按职责拆成多个文件。

**细则**：

- 每个文件只做一件事；写新功能前先回答"它属于哪个文件夹的哪个文件"，答不出来先讨论结构再动手；
- 模块对外的**唯一出口是 `index.ts`**（沿用旧 core 的约定），外部不许深路径引用内部文件；
- 单文件以一屏到两屏为宜，明显超长就拆；
- 参照范例——上一版 core 的 `read/` 模块就是这个结构：

  ```
  read/
  ├─ index.ts        # 唯一出口
  ├─ read_main.ts    # 入口：检查 → 参数校验 → 分流
  ├─ read_file.ts    # 文件子工具
  └─ read_dir.ts     # 目录子工具
  ```

## 规则五：见名知意

**原则**：变量名、函数名、类名、文件名，都要能从名字直接读出意图。

**细则**：

- 禁止 `a`、`tmp`、`x1`、`doSomething`、`handleStuff` 这类名字；
- 名字用英文，和项目统一词汇表保持一致——同一个概念永远同一个词（kernel / session / tool / host / permission…），不今天叫 `session` 明天叫 `conversation`；
- 文件名 = 文件内容的目录，看到文件名就知道该不该点进去；
- 布尔值用 `is / has / can` 前缀；异步取数用 `loadXxx / fetchXxx`；转换用 `toXxx / parseXxx`。

## AI 协作流程（把规则一、二串起来）

每个开发小节的固定节奏：

1. **对齐**：AI 讲清这一步做什么、为什么、会动哪些文件——用户确认后才进入下一步；
2. **用户写代码**：AI 不动编辑器，只回答问题和讲解；
3. **AI review**：只提问题和建议（哪里不合本规范、哪里可能有坑），不直接改；
4. **验证**：跑 typecheck / 测试，通过才 commit，小步提交；
5. **卡住时**：AI 先讲思路给提示；实在需要，才按规则二第三档申请代写那一小段。

## 违规处理

- AI 一次性生成超量代码：用户有权要求整段删掉重来；
- review 发现不符合本规范：修到符合再 commit，不带病提交。
