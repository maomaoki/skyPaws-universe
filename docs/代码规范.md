# skyPaws · 代码规范

> 这份文档约束 skyPaws 的代码怎么写、我怎么答问题。
> 目标不是「符合行业惯例」，而是「三个月后自己还能看懂、能接着写」。

> **第一条铁律：代码我为主。除我明确说「你写 / 你改 / 创建 / 编辑」，否则一律是讨论，不要动文件。**
> **第二条铁律：指令的字面范围就是全部范围。「创建文件」只建骨架，不写实现——要停一次等我发话。**（详见第四节）

## 一、注释

### 1.1 必须有注释的地方

| 位置 | 要求 |
|---|---|
| 包声明上方 | 一句话说清这个包负责什么，用 `// Package xxx ...` |
| 导出的类型 / 函数 / 常量 | 必须有 `//` 注释，写「做什么」，不写「怎么做的」 |
| 复杂逻辑块 | 上方加一行说明这段在干什么 |
| 非显然的取舍 | 写清「为什么这样」，尤其是反直觉的地方 |
| 边界条件 / 坑 | 必须写，例如「流式下这里不能超时」 |

### 1.2 不需要注释的地方

- 一眼能看懂的赋值：`name := "abc"` 不需要注释
- 代码已经说清楚了，注释只是复述：`// 循环遍历数组` ← 删掉
- 被函数名完全表达的：`readFile()` 不需要注释说「读取文件」

**判断标准**：注释要提供代码本身没有的信息。要么是意图（为什么），要么是约束（不能怎么改）。

### 1.3 注释风格

```go
// Chat 发送一条消息，返回完整回复（非流式）。
// 出错时返回的 error 已经带了状态码和响应体片段，调用方直接展示即可。
func Chat(baseURL, apiKey, modelName, prompt string) (string, error) {
```

- 用中文，句末不加句号（单行）；多行注释每行都加 `//`
- 函数注释第一行以函数名开头（Go 惯例，`golint` 会检查）
- 不用 `/** */`，Go 只有 `//` 和 `/* */`

## 二、函数内的执行流程注释

### 2.1 要求

**函数体里，关键步骤逐行或逐块加注释，说明这个变量/这一步是干什么的。**

不是每行都必须，但**读者要能顺着注释一路读下来，不用猜**。

### 2.2 反面例子

```go
func (a *Agent) RunTurn(ctx context.Context, conv *Conversation) (*Reply, error) {
	resp, err := a.provider.Complete(ctx, a.buildRequest(conv))
	if err != nil {
		return nil, err
	}
	conv.AppendAssistant(resp.Text, resp.ToolCalls)
	if len(resp.ToolCalls) == 0 {
		return &Reply{Text: resp.Text}, nil
	}
	for _, call := range resp.ToolCalls {
		conv.AppendToolResult(a.executor.Run(ctx, call))
	}
	return nil, ErrMaxSteps
}
```

能读，但**看不出设计意图**：为什么 tool_calls 为空就返回？为什么 assistant 消息要原样入历史？后来的人很容易「顺手优化」掉关键逻辑。

### 2.3 正面例子

```go
// RunTurn 推进一轮对话：从用户输入开始，循环到模型不再请求工具为止。
// 每一轮的「决策 → 执行 → 观察」都追加进 conv，conv 是唯一状态源。
func (a *Agent) RunTurn(ctx context.Context, conv *Conversation) (*Reply, error) {
	// 步数上限：防止模型反复调工具烧钱，超了就报错而不是静默返回
	for step := 0; step < a.maxSteps; step++ {
		// 组装本轮请求：system + 记忆 + 近期消息 + 工具清单
		req := a.buildRequest(conv)

		// 调模型；这里只拿 text / tool_calls，不关心底层是哪家协议
		resp, err := a.provider.Complete(ctx, req)
		if err != nil {
			return nil, err
		}

		// assistant 消息必须原样入历史（含 tool_calls 和 id），
		// 重写或省略会导致下一轮上下文对不上
		conv.AppendAssistant(resp.Text, resp.ToolCalls)

		// 没有工具调用 = 模型认为可以回答了，本轮结束
		if len(resp.ToolCalls) == 0 {
			return &Reply{Text: resp.Text}, nil
		}

		// 执行工具；结果作为 role=tool 的消息追加，模型下一轮就能看到
		for _, call := range resp.ToolCalls {
			result := a.executor.Run(ctx, call)
			conv.AppendToolResult(call.ID, result)
		}
	}

	// 走完 maxSteps 还在调工具，说明模型陷入循环，报错让上层处理
	return nil, ErrMaxSteps
}
```

**差别**：后者读一遍就知道每步为什么存在，以及哪些地方不能改。

### 2.4 变量注释

局部变量如果不是「名字自解释」的，加行尾或上方注释：

```go
// call 是模型发起的一次工具调用，Args 是 JSON 字符串（不是对象）
var call ToolCall

// truncated 表示响应体超过上限被截断，此时内容不完整，需要提示用户
truncated := len(raw) >= maxBody

// deadline 是本轮对话的绝对截止时间，不是超时时长
deadline := time.Now().Add(a.turnTimeout)
```

**不要**给 `i`, `n`, `err` 这类惯用名加注释。

## 三、命名

### 3.1 总规则

| 语言 | 规则 |
|---|---|
| Go 导出（public） | `大驼峰`：`ChatRequest`、`RunTurn`、`ToolExecutor` |
| Go 非导出（private） | `小驼峰`：`chatRequest`、`buildRequest`、`maxSteps` |
| TypeScript / JS | 变量和函数 `小驼峰`，类型和组件 `大驼峰` |
| 常量 | Go：`大驼峰`（`MaxSteps`）或全大写仅限真正的全局常量；TS：`UPPER_SNAKE` |
| 文件名 | Go：全小写无下划线（`chatrequest.go` 不行，用 `chat_request.go`）；TS：`kebab-case` 或 `camelCase` |

### 3.2 命名要表达「是什么」，不是「是什么类型」

```go
// 好
var apiKey string
var timeout time.Duration
var isStreaming bool

// 差
var keyStr string      // 类型写进名字了
var timeoutInt int     // 同上
var flag bool          // 什么 flag？
var data interface{}   // 什么 data？
```

### 3.3 常见后缀约定

| 后缀 | 含义 | 例子 |
|---|---|---|
| `...List` / 复数 | 集合 | `ToolList`、`messages` |
| `...Map` | 明确的 map | `ChatFields` |
| `...Raw` | 未解析的原始数据 | `GetModelsRaw` |
| `...WithXxx` | 在基础版本上多一个参数 | `GetModelsRawWithAuth` |
| `...Err` | 预定义错误值 | `ErrMaxSteps` |
| `...Func` / `...Handler` | 回调函数 | `onDelta` |

### 3.4 禁止

- 拼音命名（`neirong`、`huoqu`）—— 一律英文
- 单字母除了 `i`、`j`、`k`、`err`、`ok`、`ctx`、`w`、`r` 这类惯用
- 缩写除非是行业共识（`URL`、`ID`、`HTTP`、`API`、`JSON`），且**大小写要统一**：`baseURL` 不是 `baseUrl`

### 3.5 方法接收者

```go
// 单字母，取自类型名首字母，全文件统一
func (a *Agent) RunTurn(...)      // Agent → a
func (c *Conversation) Append(...) // Conversation → c
```

不要混用 `self`、`this`、`s`、`a`。

## 四、谁来写代码

### 4.1 总原则：你为主，我等你发话

**这个项目的代码由你写。我不主动编辑任何文件。**

默认状态下，我做的事情只有一件：**回答问题**。包括讲思路、解释 API、给示例、指出你代码里的问题——**全部停留在对话里，不落到文件上**。

### 4.2 什么时候我才会动文件

只有你说出明确的编辑指令，比如：

- 「你写」
- 「你改一下」
- 「把这段加进去」
- 「创建这个文件」
- 「编辑 xxx」

**没有这类指令，一律按讨论处理。**

以下几种说法**不算**编辑授权，我只会回答、不会动手：

| 你说的话 | 我的反应 |
|---|---|
| 「这样写对吗？」 | 判断对错，指出问题，**不改文件** |
| 「这个报错怎么办？」 | 解释原因 + 给修改示例，**不改文件** |
| 「是不是应该用 X？」 | 讨论 X 和 Y 的取舍，**不改文件** |
| 「这块我不太懂」 | 讲解原理 + 举例，**不改文件** |
| 「我觉得这里有问题」 | 帮你确认问题在哪，**不改文件** |
| 「你会怎么设计？」 | 给设计方案和代码片段，**不落盘** |

### 4.3 讨论和编辑的分界

```
你说的话
   ↓
有没有明确的「你来写 / 你改 / 创建 / 编辑」这类指令？
   ├─ 没有 → 讨论：解释 + 示例代码（放在对话里，方便你复制或对照）
   └─ 有   → 编辑：动手改文件，改完说明改了什么
```

**不确定的时候，我默认按讨论处理，并问你一句「需要我直接改吗」。** 宁可多问一次，不擅自落盘。

### 4.4 授权的粒度：「创建文件」不等于「实现功能」

**指令的字面范围就是全部范围，不做任何外推。**

| 你说的话 | 我只做这些 | 我绝不做这些 |
|---|---|---|
| 「创建一个文件 xxx」 | 建文件：包声明 + 空的类型 / 接口骨架 + 一句 TODO | 写完整实现、写业务逻辑、顺手补测试 |
| 「实现 xxx」/「写 xxx」 | 按你的要求写这个功能的完整代码 | 顺手加别的功能、改别的文件 |
| 「补一个 xxx 函数」 | 只写这个函数 | 顺带重构调用它的地方 |
| 「看看这个文件」 | 读并分析，不动手 | 任何修改 |

判断顺序：

```
你的指令
   ↓
落到文件上吗？
   ├─ 不落（问、看、讨论）→ 只在对话里回答
   └─ 落（创建 / 编辑 / 写）
        ↓
     说的是「文件」还是「功能」？
        ├─ 文件 → 只建骨架，函数体留空 + TODO
        └─ 功能 → 写完整实现
```

**「创建」和「实现」是两个动作，中间要停一次等我说。** 我说创建，你就只创建。

骨架的标准是：能编译通过，但函数体是空的或只有 `panic("TODO")` / `return nil, ErrNotImplemented`。

### 4.5 讨论时我给的代码是什么

对话里的代码**是给你参考的，不是要你照抄**：

- 可以是完整函数，也可以是片段
- 标明哪些是关键点、哪些可以按你的习惯改
- 不假设你会用它替换现有代码

### 4.6 你说「你写」的时候

- 写完必须能 `go build` / `go vet` 通过
- 按本文档的注释和命名规范写
- 写完说明改了哪些文件、为什么这么设计
- 不引入新依赖，除非你同意

### 4.7 我改你的代码时

- 只改和当前任务相关的部分
- 发现别的毛病，**说出来但不擅自改**
- 改动超过 20 行，先说方案

## 五、我怎么回答问题

### 5.1 三件套：结论 → 例子 → 流程

每次技术问答，按这个顺序：

1. **结论先行** —— 一两句话给判断，不要铺垫
2. **代码例子** —— 具体到能跑、能对照
3. **执行流程** —— 数据怎么流动、谁调谁

### 5.2 例子要求

- **能直接对照的对比**：错误写法 vs 正确写法，而不是只给一个正确版本
- **用项目里的真实名字**：`core/llm/chat.go`、`RunTurn`、`tool_calls`，不用 `Foo`、`Bar`
- **代码要能跑**：给 Go 就应该是合法 Go，不是伪代码（除非明说「这是伪代码」）

### 5.3 流程图

**能画就画。** 用 ASCII 图，因为终端里能直接看：

```
用户输入
   ↓
组装上下文（system + 记忆 + 近期消息 + 工具清单）
   ↓
调模型 ──► 返回 tool_calls？
   │            │
   │ 否         │ 是
   ↓            ↓
返回文本      执行工具
                ↓
            追加 tool 消息
                ↓
            回到「调模型」
```

需要表达结构时用表格：

| 层 | 职责 | 有 LLM 吗 |
|---|---|---|
| 大脑 | 决策、循环 | 有 |
| harness | 执行、上报 | 没有 |

### 5.4 什么时候可以省略

- 纯粹的事实性回答（「Go 里 map 是引用类型吗」）—— 一句话就够
- 你明确说「简短说」

**但只要涉及设计取舍、架构选择、协议对比，三件套不能省。**

## 六、其它约定

### 6.1 错误处理

- 错误信息用中文，带上下文：`fmt.Errorf("读取配置 %s 失败: %w", path, err)`
- 用 `%w` 包装，不要用 `%v` 吞掉错误链
- 对外返回的错误要能直接展示给用户看

### 6.2 文件组织

```
core/
  bootstrap/   启动初始化、全局变量
  cmd/         程序入口
  config/      配置读取
  llm/         模型 API 调用
  study/       学习用的字段说明、协议示例
```

**一个包一个职责。** 新增能力优先开新包，不要往 `llm` 里堆业务逻辑。

### 6.3 提交前检查

```bash
go vet ./...
go build ./...
gofmt -l .        # 应该没有输出
```

（本机 `go` 不在 PATH 里，实际路径 `D:\ym\go-1.27.4\bin`）

### 6.4 不要做的事

- 不写 `TODO` 就交付 —— 要么现在做，要么写进 `docs/skyPaws-想法.md`
- 不留注释掉的代码 —— git 里有历史
- 不加没用的抽象 —— 三个相似函数不需要先抽接口
- 不为了「以后可能用到」加参数
